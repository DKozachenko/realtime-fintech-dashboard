# Realtime Fintech Dashboard — дизайн

Дата: 2026-11-02. Исходные требования: `Technical Specifications/`. Решения с обоснованиями — в `DECISIONS.md` (на английском); здесь — что строим и как это устроено.

## 1. Что это

Демо-дашборд рынка в реальном времени — как мог бы выглядеть фронтенд трейдинговой платформы. Wasm-генератор изображает рыночный фид (вместо бэкенда), воркер — клиентскую обработку потока, Angular — интерфейс.

Принципы:
- каждое решение объяснимо, а сделанное сверх требований явно помечено как собственный выбор (DECISIONS.md);
- код простой, его легко менять;
- каждый push автоматически доезжает до живого демо;
- история коммитов осмысленная, по шагам, а не одним коммитом.

## 2. Цели, не-цели, анти-цели

**Цели** — всё из задания: дашборд с 5 метриками, Pause/Resume и статусом; страница настроек с валидацией и Apply; генератор на Rust → Wasm внутри Web Worker; юнит-тесты по списку задания; GitHub-репозиторий с README и автодеплоем на GitHub Pages.

**Не-цели** (сознательно не делаем):
- SharedWorker и синхронизация между вкладками — у каждой вкладки свой независимый прогон;
- сохранение настроек/прогона между перезагрузками;
- сортировки и фильтры таблицы, virtual scroll (≤ 50 строк);
- реалистичная биржевая модель, матчинг заявок, связь дисбаланса со сторонами сделок;
- подключение Sentry (только абстракция логгера);
- e2e-тесты.

**Анти-цели** (провал, даже если «работает»):
- метрики генерируются случайно, а не считаются из сделок;
- хоть одна сгенерированная сделка не попала в volume/VWAP;
- данные старого прогона перезаписали новый;
- интерфейс тормозит при 1000 обновлений / 50 мс;
- случайность или логика цен фактически живёт в JS.

## 4. Термины

- **Инструмент** — выдуманный актив с тикером (`ALFA`, `BETA`, …). Одна строка таблицы = один инструмент; их число = настройка Instrument count (1–50).
- **Обновление** — одна сделка + текущий снимок лучших bid/ask по одному инструменту.
- **Батч** — пачка обновлений, которую генератор возвращает за один вызов. Её размер задаёт настройка Updates per batch; инструменты в ней выбираются случайно, могут повторяться или отсутствовать.
- **Прогон (run)** — последовательность батчей с одним `runId` и одними настройками. Начинается при старте приложения и по Apply. Pause/Resume прогон не меняют.
- **Снимок (snapshot)** — готовые метрики всех инструментов, которые воркер отправляет в Angular.

## 5. Архитектура и поток данных

```
Angular (main thread)            Worker (TS)                          Wasm (Rust)
─────────────────────            ───────────                          ───────────
ProducerService (root, один) ─команды─▶ ProducerEngine:               Generator:
  activeSettings, runId,               таймер батчей, runId,  ─next_batch(n)─▶ состояние инструментов,
  status, snapshot (signals)           агрегатор метрик       ◀─Uint32Array──  rand_pcg(seed)
        ▲                              │
        └──────── снимок (≤ 50 строк, ≤ 4 раз/с) ◀┘
Dashboard / Settings (OnPush, pipes только форматируют)
```

Распределение ответственности:
- **Wasm** генерирует только сырые обновления. Названий инструментов не знает — работает с номерами.
- **Worker** владеет таймером, вызывает генератор, считает метрики на TypeScript, решает, когда отправить снимок.
- **Angular** хранит состояние прогона в сигналах, отбрасывает снимки прошлых прогонов (см. 5.5), рисует и форматирует.

Логика воркера — обычный TS-класс `ProducerEngine` с подставляемыми зависимостями (генератор, планировщик таймеров, источник seed, функция отправки сообщений). Файл воркера — тонкая обёртка: загрузить Wasm, создать движок, пробросить `onmessage`/`postMessage`. Так движок тестируется в Karma без настоящего воркера и без реальных ожиданий.

### 5.1 Формат батча (Wasm → Worker)

Плоский `Uint32Array`, 7 чисел на обновление, подряд:

| # | поле | пример |
|---|---|---|
| 0 | instrument index (0…N−1) | 0 |
| 1 | priceCents | 10200 |
| 2 | tradeQuantity | 30 |
| 3 | bidCents | 10196 |
| 4 | askCents | 10200 |
| 5 | bidQuantity | 600 |
| 6 | askQuantity | 400 |

Rust пишет в собственный переиспользуемый буфер; JS читает его без копирования: `new Uint32Array(memory.buffer, ptr, size * 7)`. **Представление создаётся заново на каждый батч** — при росте памяти Wasm старый `buffer` становится detached. Агрегатор читает поля по именованным смещениям (`BatchField.Price` и т. п.), не создавая объект на каждое обновление; в тестах батчи собираются обратной функцией `encodeUpdates`.

### 5.2 Сообщения

Angular → Worker:
- `start { runId, settings }` — новый прогон (и старт приложения, и Apply);
- `pause { runId }`, `resume { runId }`;
- `dispose`.

Worker → Angular:
- `ready` — Wasm загружен;
- `snapshot { runId, rows, tradesCounted }`;
- `error { runId?, source: 'wasm' | 'worker', message }`.

`rows[i]` для инструмента `i`: `{ lastPriceCents, spreadCents, volume, vwapCents, imbalance }`, где всё, кроме `volume`, — `number | null`. VWAP передаётся **неокруглённым**. Тикер не передаётся — Angular берёт его из общей функции `instrumentSymbol(i)`.

Команды, пришедшие до загрузки Wasm, воркер выполняет после неё (не теряет).

### 5.3 Состояние и метрики в воркере

На инструмент — фиксированный набор чисел, история не хранится:
- перезаписываются последним обновлением: last price, bid, ask, bidQty, askQty;
- накапливаются по каждому обновлению: `volume = Σqty`, `pv = Σ(price × qty)`.

Метрики (из задания):
- **Last price** — цена последней сделки;
- **Spread** = `ask − bid`;
- **Volume** = `Σqty` с начала прогона (стакан не учитывается);
- **VWAP** = `pv / volume`, `null` при `volume = 0`;
- **Imbalance** = `(bidQty − askQty) / (bidQty + askQty)`, `null` при нулевом знаменателе.

Инструмент, ещё ни разу не встретившийся в прогоне: все значения `null`, объём 0. Инструмент, пропущенный в очередном батче, сохраняет прежние значения. `tradesCounted` — общее число учтённых обновлений в прогоне.

Тип чисел — `number` (обоснование и расчёт предела — в DECISIONS.md).

### 5.4 Таймер, частота снимков, команды

Один таймер в воркере — интервал батча (настройка Batch interval). Снимок отправляется на каждом N-м батче:

```
N = max(1, round(DISPLAY_INTERVAL_MS / batchIntervalMs)),  DISPLAY_INTERVAL_MS = 250 (≈ 4 раза/с)
```

| Команда | Поведение воркера |
|---|---|
| start | остановить таймер → `free()` старого генератора → новый генератор (новый seed) и пустое состояние → запустить таймер. Если прогон был на паузе — всё равно запускается (по заданию) |
| pause | остановить таймер → **сразу** отправить снимок с точными итогами |
| resume | запустить таймер; первый батч — через один интервал (быстрые Pause/Resume не ускоряют генерацию); пропущенное время не догоняется |
| dispose | остановить таймер, освободить генератор |

Команды pause/resume с чужим `runId` игнорируются.

### 5.5 ProducerService (Angular)

- `providedIn: 'root'` — один на приложение; создаёт **один** воркер; навигация его не пересоздаёт.
- Состояние — один приватный сигнал; наружу только `computed`: `activeSettings`, `runId`, `status` (`initializing | running | paused | error`), `rows`, `tradesCounted`, `errorMessage`.
- Старт приложения: прогон с дефолтами (5 / 100 / 500).
- **Apply**: новый `runId` → `activeSettings` = новые значения → **сразу** пустая таблица на N строк (`null` и объём 0) → `start` в воркер.
- **Снимки прошлых прогонов отбрасываются** — всё, у чего `runId` не равен текущему. Откуда они берутся: `postMessage` асинхронный. Воркер мог отправить снимок старого прогона за мгновение до того, как получил `start`, и этот снимок дойдёт до Angular уже после Apply. То же с финальным снимком после Pause, если сразу за ним нажали Apply. Без фильтра такой снимок перезаписал бы пустую таблицу нового прогона старыми итогами.
- Pause/Resume: команды воркеру, статус меняется сразу.
- Статусы: `initializing` до сообщения `ready` от воркера, затем `running`. Пустая таблица включает `tradesCounted = 0`.
- Ошибки: `worker.onerror` и сообщения `error` → статус `error`, текст ошибки, таймер в воркере остановлен.
- **Retry** (моё): `terminate()` воркера → новый воркер → новый прогон с `activeSettings`. `terminate()` уничтожает всё внутри воркера, включая экземпляр Wasm, его память и генератор, поэтому отдельный `free()` не нужен. Новый воркер — потому что после ошибки старому нельзя доверять: скрипт мог не загрузиться, а после паники в Rust экземпляр Wasm остаётся в неопределённом состоянии. Один путь «пересоздать всё» покрывает все случаи; цена — повторная загрузка небольшого `.wasm`, который браузер уже закэшировал. Apply в состоянии `error` работает так же, как Retry, но с новыми настройками.
- Очистка: при уничтожении сервиса (`ngOnDestroy`) — `dispose` и `terminate()` воркера.
- Источник воркера подставляется через фабрику (DI-токен), чтобы тесты сервиса работали с фейковым воркером.

### 5.6 LoggerService

Абстракция: `log/warn/error(source, message, context)`, где `source ∈ app | worker | wasm`, контекст включает `runId`. Реализация сейчас — консоль; позже можно подменить на Sentry без правок остального кода. Ошибки воркера пересылаются сообщением и логируются в Angular.

## 6. Генератор (Rust → Wasm)

**Из задания:** состояние по инструментам между вызовами; батч ровно запрошенного размера; цена эволюционирует от предыдущей; цена > 0, bid < ask, количество в сделке > 0, количества стакана ≥ 0; цена сделки = bid или ask; случайность и логика цен — в Wasm; реалистичная модель не нужна.

**Модель (собственный выбор; все числа — константы в одном месте):**
- Старт прогона: на инструмент `mid` — случайная цена $10–$500, `anchor = mid`; bidQty/askQty — 100–1000.
- Каждое обновление:
  1. инструмент — равновероятно из 0…N−1;
  2. `mid` сдвигается на случайный шаг ≈ ±0.1% + лёгкое притяжение к `anchor`; нижняя граница, чтобы bid ≥ 1 цента;
  3. спред 1…несколько центов (всегда ≥ 1): `bid = round(mid − spread/2)`, `ask = bid + spread`;
  4. bidQty/askQty — случайный шаг от прошлых значений, не ниже 0 (иногда 0 — даёт реальный случай нулевого знаменателя);
  5. сторона сделки 50/50: покупка → цена = ask, продажа → цена = bid;
  6. количество в сделке 1–500.
- Внутри `mid` — `f64`, наружу — только целые центы.

**Случайность:** `rand_pcg`, инициализируется `seed_from_u64(seed)`. Seed **генерирует воркер** на каждый `start` (`crypto.getRandomValues`) и передаёт в `Generator::new`; в тестах движку подставляется фиксированный seed. Это единственное случайное число из JS за прогон — все остальные считаются в Rust. Никаких обращений к системной энтропии (`thread_rng`/`OsRng`).

**API (wasm-bindgen):**
```
Generator::new(instrument_count, seed)   ошибка, если count ∉ 1..=50
generator.next_batch(size) -> u32        заполняет внутренний буфер; ошибка, если size ∉ 1..=1000
generator.batch_ptr() -> *const u32      адрес буфера в памяти Wasm
generator.free()                          освобождение (Apply / dispose)
```
Буфер переиспользуется между вызовами. Валидация в Rust дублирует форму — защита от ошибок вызывающего кода.

## 7. Интерфейс

Утверждены макеты: **дашборд B** и **настройки B** (`docs/superpowers/mockups/dashboard.html`, `docs/superpowers/mockups/settings.html`; в каждом файле два варианта, выбран B). Все тексты — на английском.

**Визуальный язык:**
- палитра: фон `#06110d`, панели `#0b1c16`, линии `#1a3329`, текст `#e3efe8`, вторичный текст `#7e9b8d`, рост/акцент `#8fe3b6`, падение `#ee8a96`, пауза `#e9c46a`; градиент `linear-gradient(120deg, #0b2f22, #125238, #1d7a54)` — плашка страницы, логотип, основная кнопка;
- шрифт Manrope (Google Fonts), цифры `font-variant-numeric: tabular-nums`, чтобы столбцы не прыгали;
- видимый фокус с клавиатуры, `prefers-reduced-motion` отключает пульсацию.

**Каркас:** левая панель-рельс (логотип + иконки Dashboard / Settings с подсказками), справа — градиентная плашка страницы и контент. Мобильной версии нет — не требуется; на узком экране таблица скроллится горизонтально.

**Дашборд:**
- плашка: заголовок «Live market»; Status (точка: Running — пульсирующая мятная, Paused — янтарная, Initializing — серая, Error — розовая); Run `#N`; Nominal rate `= updatesPerBatch × 1000 / batchIntervalMs` в `/ s`; Trades counted; кнопка Pause/Resume (неактивна в Initializing и Error);
- таблица: Instrument | Last price | Spread | Volume | VWAP | Imbalance;
- цены — валюта USD, 2 знака (`$101.50`), округление только в pipe; объём — целое с разделителями; imbalance — со знаком, 2 знака (`+0.20`) + шкала −1…+1 с риской в нуле (зелёная вправо, розовая влево); нет значения — «—»;
- last price: стрелка ▲/▼ и короткая цветная подсветка при изменении относительно предыдущего снимка;
- ошибка — баннер под плашкой: что сломалось + что делать, кнопка Retry. Пример: «Generator failed to load. … Check that generator_bg.wasm is deployed, then retry.»

**Настройки:**
- плашка «Producer settings» со статусом и номером прогона;
- слева форма: Instrument count / Updates per batch / Batch interval, ms — у каждого описание, диапазон, поле;
- валидация (Reactive Forms): обязательно, целое, в диапазоне. Ошибка показывается после ухода с поля или попытки Apply. Тексты: «Enter a value.», «Enter a whole number.», «Must be between 1 and 50.»;
- **Apply** активна, только если форма валидна **и отличается от `activeSettings`** (сравнение со значениями прогона, не флаг `dirty`); подсказка на неактивной кнопке «Change a setting to apply it»;
- **Reset to defaults** — возвращает в форму 5 / 100 / 500 (сам прогон не трогает);
- справа панель «What Apply will change»: Active run vs After Apply по трём настройкам и Nominal rate; изменённые значения подсвечены; подпись «Apply starts a new run: values and totals on the dashboard reset to zero.»;
- после Apply пользователь остаётся на странице, видит подтверждение «Run #N started: …»; форма при этом совпадает с новым прогоном → Apply снова неактивна;
- при возврате на страницу форма инициализируется из `activeSettings` (несохранённые правки при уходе со страницы теряются — моё).

## 8. Тесты

Требование задания → где проверяем:

| Задание | Тесты |
|---|---|
| Метрики: пример из задания, нулевые знаменатели, изоляция инструментов | агрегатор (Karma): 10×$100 + 30×$102 → last $102, volume 40, VWAP 10150¢; bid 10196 / ask 10200 → spread 4¢; 600/400 → +0.20; volume 0 → VWAP null; 0/0 → imbalance null; обновления ALFA не трогают BETA; пропущенный в батче инструмент сохраняет значения |
| Валидация и сброс при Apply | форма: границы 0/1/50/51 и т. д., дробные, пустые; Apply неактивна при невалидной/неизменённой форме; сервис: Apply → новый runId, пустая таблица, `activeSettings` |
| Pause/Resume и отбрасывание старого прогона | движок с фейковым таймером: pause останавливает генерацию и сразу шлёт снимок; resume не догоняет и ждёт интервал; итоги сохраняются; start из паузы запускает; сервис игнорирует снимок с прошлым runId |
| Генератор: размеры батчей, валидные значения | `cargo test`: длина = size × 7 для 1/100/1000; ~100 000 обновлений с фиксированным seed — price > 0, bid < ask, price ∈ {bid, ask}, qty > 0, index < N; цена меняется ограниченным шагом; второй батч продолжает состояние первого; одинаковый seed → одинаковый выход; ошибки на 0/51 и 0/1001 |
| Плюс | частота снимков: `N` для 50/100/200/500/2000 мс; декодер батча; pipes форматирования |

Никаких реальных ожиданий: таймеры подставные (`fakeAsync` или собственный планировщик).

## 9. CI/CD (GitHub Actions)

Триггеры: push в `develop`, pull_request, workflow_dispatch.

```
cache-deps ─┬─▶ deploy   Rust + wasm-pack → ng build --base-href=/realtime-fintech-dashboard/ → peaceiris/actions-gh-pages (только push в develop)
            ├─▶ test     cargo test + ng test (ChromeHeadless)
            └─▶ lint     ESLint, stylelint, cargo clippy/fmt — добавляется последним
```

- **Деплой не зависит от тестов** (осознанно: изменения на демо появляются быстрее; красный тест виден отдельно).
- GitHub Pages публикует ветку `gh-pages` (корень). Её создаёт первый деплой; до этого Pages выключен.
